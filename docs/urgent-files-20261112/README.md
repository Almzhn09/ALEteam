# P0-A1 — файлы при обновлении постоянной БД

Причина: новая Cloud Run сборка импортирует источник в свежий snapshot, создавая случайные staging storageKey. Neon сохраняет записи прежнего snapshot. Копирование новой папки files не восстанавливало файлы под прежними путями: фото и оригиналы отдавали404. Ошибка воспроизведена по трём фотографиям публичной главной; публичная версия до этого исправления ещё не обновлена.

Исправление startup: создать индекс неизменных байтов нового bundled snapshot по SHA256; восстановить мастера и превью опубликованных CmsAttachment в пути, записанные в текущей постоянной БД. ID/пути/записи и пользовательские данные БД не переписываются. Доступ, публикация редакции и права по-прежнему проверяются штатным API. Неизвестный пользовательский файл не подменяется похожим источником; новые загрузки вне bundled corpus по-прежнему требуют постоянного файлового хранилища.

Проверки: 6 модульных сценариев (разные пути двух сборок, повтор, отсутствующий hash, traversal, source/destination symlink, конфликт); восстановлены42файла для30опубликованных вложений в независимые пути реального `_test` корпуса из другого Docker snapshot. Через production HTTP все42оригинала/превью вернули200 и точный SHA256:18DOCX,9PDF,12PNG,3JPEG. [Отчёт](restored-http.json). Рабочая Neon не изменялась. Этот отчёт подтверждает локальную проверку исправления; публичную выдачу нужно проверить после развёртывания.

Дополнительно усилена `tests/cloud-run-persistent.mjs`: после первого запуска в собственной одноразовой БД заменяются все staging-пути, затем контейнер перезапускается. Проверяются42оригинала/превью по SHA256, прежний ID исходной страницы, произвольная сохранённая строка и прежняя сессия администратора.4сценария прошли: [отчёт](container-restart.json). Для этой адресной проверки использован прежний локальный образ приложения с обновлёнными runtime-модулями; это проверка startup/файлового восстановления, не новая полная сборка всех интерфейсных доработок.

Дополнительно устранено ограничение самого сохранённого DOCX-excerpt: новый `?reader=1&offset=N` читает разрешённый оригинал отдельным ограниченным worker и отдаёт следующие12k-части полного текста, не переписывая существующий parsed и не расширяя контекст ИИ. Унаследованный API без reader=1 сохраняет прежнее поведение. Проверки worker: длинный абзац/последний абзац, неправильный offset, подмена SHA; типы и9целевых тестов проходят. Исходный DOCX не меняется. Интерфейс дозагрузки принимается отдельным frontend-коммитом.
