# B08 / R-A04 — staging и импорт метаданных в черновики

Миграция `202611100002_catalog_import_staging`, затем `npm run db:generate`. Используются существующие каталог/редакции/согласование; импорт не создаёт вторую систему публикации. Это основной путь **JSON-метаданных**, не перенос реального архива, файлов/всех исторических полей или готовый CSV/XML-конвертер.

## Манифест

[Браузерные типы](../../src/contracts/imports.ts), [строгая серверная схема](../../src/server/catalog-import-schema.ts), [собственный демонстрационный пример](../../data/artur/import-fixture.json).

`version=1`, существующий branchId, sourceNamespace, isDemo, массивы funds/inventories/cases/documents. Namespace — стабильный идентификатор исходного набора; sourceId — исходный идентификатор документа, не название и не автоматически придуманный ID. Учётные номера и sourceId — строки. `0007`, `0001`, `0003/А`, `000009` сохраняются буквально, Unicode/NFKC-нормализация и преобразование в числа не выполняются. Номера с краевыми пробелами отвергаются. Текстовые поля проходят те же trim/ограничения, что действующий каталог.

Fund имеет локальный key, number, name, description; inventory — key/fundKey/number/title; case — key/inventoryKey/number/title. Document — sourceId/fundKey/caseKey (либо null), metadata RU и необязательные translations.kk/en. Metadata соответствует действующему DocumentMetadataInput, но **caseId запрещён**: внутренние FK разрешает сервер из ключей манифеста. Перевод содержит только DocumentTextInput, не год/оригинальный язык/права на копию/родителя. Отсутствующие переводы не копируются с RU и не придумываются.

Ключи, sourceId, номера внутри одного родителя и шифры проверяются на дубли. Одинаковый номер дела в разных описях разрешён. Отсутствующий родитель или дело другого фонда — ошибка с путём/индексом строки. Исходные namespaces/ID и их contentHash сохраняются в отдельной таблице. Для недемонстрационных записей требуется происхождение каждой переданной языковой версии. Поле rights обязательно; юридическое разрешение и языковой перевод всё равно подтверждает человек.

Строго запрещены status/isPublic, authorId/reviewerId, private notes, пути/байты файлов, внутренний caseId и лишние поля. sourceUrl допускает HTTP(S) без учётных данных; импорт его **не запрашивает**. Формат ограничен 100 документами и 100 узлами каждого типа, запросом 2 MiB. Больший набор нужно обрабатывать согласованными частями или будущим пакетным процессом; работа на реальном архивном объёме не заявляется.

## API и права

Все `/api/admin/imports` — активная сотрудническая сессия; изменения проходят same-origin. Чтение/экспорт требует `catalog.read`, создание/проверка/commit/cancel/rollback — также `catalog.write` **в филиале пакета**. Один филиал не даёт прочитать чужой пакет или его sourceManifest; аналитик/посетитель не могут импортировать. Манифест после staging неизменяем. Ни один endpoint не принимает личность сотрудника или новый текст существующей записи для тихой перезаписи.

| Запрос | Поведение |
|---|---|
| POST /admin/imports с манифестом | 201 `{item}` READY или VALIDATION_FAILED. Создаёт только staging-запись/отчёт; фонды, документы, редакции и публикации не меняются |
| GET /admin/imports?branchId=...&page=1&pageSize=20 | Список только своей области, без тяжёлого manifest |
| GET /admin/imports/:id | Сам пакет, manifest, digest, row report и состояние |
| POST /admin/imports/:id/validate | Новая проверка исходного неизменённого manifest на текущей БД |
| POST /admin/imports/:id/commit | Явное подтверждение. Повторная проверка, атомарное создание недостающей иерархии и **только DRAFT** редакций |
| POST /admin/imports/:id/cancel | Отмена незавершённого плана; архив не меняется, staging/аудит сохраняются |
| POST /admin/imports/:id/rollback | Мягкий откат только неизменённых черновиков, впервые созданных этим пакетом |
| GET /admin/imports/:id/export | Контрольный JSON: sourceManifest, digest, актуальная проверка и фактические поля/языковые редакции целевых записей |

Все POST-действия с ID принимают `{expectedUpdatedAt:"ISO",digest:"<SHA-256>"}`. Несовпадение/неверное состояние — 409 STALE_IMPORT. Уже успешно выполненный commit с тем же digest возвращает тот же результат без новых записей, даже если ответ на первый запрос был потерян. Одновременные commit сериализуются общим catalog lock и блокировкой staging-строки. Чужая роль/область проверяются заново на каждом запросе.

`report.valid` и общий state важнее отдельных счётчиков: counts.create — планируемое количество, а не количество записанных строк при ошибочном пакете. Фактически созданные ID/редакции/исходные версии находятся в createdDocuments после commit. Ошибки — `{path,code}`, индекс строки начинается с 0. Интерфейс может показать его пользователю как строку index+1.

Квота — 20 незавершённых планов автора, создание 10/минуту, действия 30/минуту; это технические ограничения прототипа, не сроки архивного хранения. Настройка регламентов и длительная история остаются задачей эксплуатации/архива. В аудит входят ID операций/сущностей, не тело манифеста и не приватные примечания.

## Повтор и защита чужих изменений

Соответствие `(branchId,sourceNamespace,sourceId)` уникально и привязано к созданному Document. Хеш включает нормализованные поля/переводы и буквальные учётные связи. Перестановка верхних массивов не меняет digest. Смена leading zeros/родителя/перевода меняет данные, а не считается косметикой.

Если источник уже импортирован с тем же хешем и его нужные поля/редакции в БД не изменены — UNCHANGED, новая редакция/документ не создаются. Изменённый источник, правка сотрудника, изъятый источник или конфликт существующего шифра — BLOCKED; автоматической перезаписи/обновления версии нет. Существующие узлы иерархии повторно используются лишь при совпадении их полей; импорт не обходит запрет переименования действующих фондов. В этой схеме reference уникален по всему каталогу: коллизия между филиалами тоже требует решения, шифр не подменяется выдуманным префиксом.

Проверка при commit выполняется повторно под транзакционной блокировкой: READY час назад не является обещанием успеха сейчас. Конфликт приводит к 409 IMPORT_CONFLICT без частично созданного дерева. Для актуального отчёта вызвать validate; исправленный исходный манифест — новый staging-пакет. Нельзя незаметно отредактировать ранее подтверждённый digest.

## Публикация и откат

Commit создаёт документ с isPublic=false и allowDigitalCopy=false, независимые версии RU/KK/EN — DRAFT, reviewerId=null. Запрошенный metadata.allowDigitalCopy может остаться лишь предложением в RU-черновике; никакие байты/индексы переводов автоматически не открываются. Нет DocumentTranslation до обычной публикации. Импорт не делает официальные сведения достоверными сам по себе.

Сначала проходит обычное независимое согласование/публикация RU. Подготовленные EN/KK-черновики имеют исходную catalogBaseVersion; после публикации/смены основы их надо обновить и согласовать по действующей версии. Попытка отправить устаревший перевод отвергается штатным CATALOG_SOURCE_CHANGED. Публикация/отзыв/закрытая копия продолжают использовать существующие серверные правила.

Rollback не удаляет историю: только впервые созданные неизменённые DRAFT-документы становятся закрытыми/удалёнными, их редакции ARCHIVED с событием. Учитываются timestamps/состав редакций и отсутствие файлов, загрузок, комментариев, избранного и любой публикации. Если хоть одна запись менялась/проверялась/публиковалась или получила новую работу, весь откат отвергается 409 IMPORT_ROLLBACK_CHANGED. Уже существовавшие UNCHANGED-документы не затрагиваются. Это не откат базы из резервной копии.

Учётные узлы, source mapping и аудит сохраняются. Поэтому после мягкого отката физическое количество строк не обязано вернуться к исходному: проверяются состояния/связи, а не фиктивная «чистая база». Повтор того же sourceId не воскрешает отменённый материал. Восстановление/разрешение конфликта — отдельная операция сотрудника; автоматического обхода нет.

## Контрольный экспорт и границы

Экспорт читает фактические редакции/связи и проверяет их с исходным manifest в одном RepeatableRead-снимке. Содержит также UNCHANGED-цели другого повтора того же набора. Для повторного staging передаётся sourceManifest, а не весь внешний аудит-объект. Изменение сотрудником видно как несовпадение, а sourceManifest остаётся исходным. Не выдаёт internalNotes, исходные байты/ключи файлов, приватные причины решений, author/reviewer в редакциях или пароли. Экспорт сотруднический, не публичная выгрузка закрытых материалов.

Это контроль переноса метаданных конкретного набора, не полный экспорт всех данных/мастеров/производных сайта и не готовый адаптер произвольного старого XML/CSV. Реальный разрешённый экспорт архива, контрольные количества/хеши его файлов, юридическое/языковое ревью и миграция больших объёмов остаются зависимостями A01/A04/A10. Пакет демонстрационных данных не выдаётся за реальную миграцию.

Проверки: `npm test`, typecheck/i18n/build, `npm run test:imports` на собственной `_test` БД. Девять HTTP-сценариев проверяют staging без изменений архива, конкурентный commit, строки/родителей/языки, повтор/контрольный экспорт, конфликты и повторную проверку, мягкий откат, запрет отката после правки/новой загрузки/публикации, обычные языковые gates, права/квоту/аудит. Это реальные API/PostgreSQL на собственных демоданных, не моки и не независимая приёмка архива.
