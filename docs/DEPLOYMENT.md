# Запуск и развёртывание

## Локальная разработка

Node.js 24 LTS (минимум 22.21), npm, Docker с Compose. Команды выполняются из корня ALEteam. Использовать существующий checkout; отдельный worktree не нужен. npm использует игнорируемый локальный кэш `.local/npm-cache`, поэтому не требуется запись в домашний каталог облачного пользователя.

```sh
npm ci
npm run setup:local
docker compose up -d --wait db
npm run db:generate
npm run db:migrate
npm run db:seed
npm run dev
```

Внутренняя проверка: `curl -fsS http://localhost:3000/api/health`, затем `/api/documents?q=библиотека`. Health проверяет SQL-запрос, а не только открытый порт. Текущая главная — техническая страница, дизайн будет делать Алинур.

`setup:local` создаёт `.env` с криптографически случайными паролями, ключом сессий, адресом PostgreSQL и правами 0600. Уже существующий `.env` не перезаписывается. Не добавлять его в Git. В примере `.env.example` только безопасные шаблоны; CHANGE_ME нужно заменить, а не использовать как реальный пароль.

Демоучётные записи: `author@example.test` и `moderator@example.test`. Пароли — DEMO_AUTHOR_PASSWORD / DEMO_MODERATOR_PASSWORD из локального окружения; не отправлять их в чат и не хранить в README. В браузере авторизацию подключает Алинур, сейчас можно использовать API-клиент с приватным cookie jar. Публичная регистрация выключена.

Seed запускается только с `ALLOW_DEMO_SEED=1`. Он повторяемо добавляет 20 вымышленных документов и 5 оригинальных тестовых PDF; это не импорт официального архива. Не сбрасывает существующие пароли/роли. Для другого пароля уже созданной учётной записи нужна отдельная административная процедура, повторный seed его не меняет.

## Проверки

```sh
npm run db:generate
npm run typecheck
npm test
npm run build
```

Для интеграционных тестов создать отдельную БД, если она ещё не существует:

```sh
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" archive_test'
npm run test:integration
```

TEST_DATABASE_URL должен указывать на выделенную БД с суффиксом `_test`. **Тесты удаляют из неё пользователей, сессии, комментарии, жалобы и историю решений.** Они сами применяют миграции, seed, запускают production-сервер на 3081 и локальные тестовые сервисы, а затем останавливают их. Для повторных запусков БД пересоздавать не нужно. Порт 3081 должен быть свободен. Тестовые сервисы проверяют контракт; они не подтверждают качество реального ИИ/анти-мата.

CI повторяет установку по lockfile, генерацию, типы, модульные тесты, сборку без секретов и HTTP-тесты с PostgreSQL. Сам факт наличия workflow не означает, что GitHub Actions уже выполнил его.

## Production-процесс и перезапуск

```sh
npm run build
npm run start
```

Перед запуском задать DATABASE_URL, BETTER_AUTH_URL (точный публичный HTTPS origin), BETTER_AUTH_SECRET (случайный ключ длиной ≥32 символов), FILE_STORAGE_ROOT. Локально допустим `http://localhost:3000`; в публичной конфигурации требуется HTTPS. Меняя ключ сессий, учитывать отзыв старых cookie. Отключить демоseed на реальных данных; учётные записи примеров нельзя переносить в публичный сервис.

Установленные зависимости, БД и файлы сохраняются; процесс приложения после восстановления машины нужно запускать заново. Для локального возврата достаточно `docker compose up -d --wait db`, `npm run db:migrate`, `npm run start` (или dev). Не удалять volume для обычного перезапуска.

Для хостинга нужны постоянная PostgreSQL, приватное файловое хранилище/volume, процесс Node.js, HTTPS reverse proxy, менеджер секретов и запуск миграций до трафика. Ограничить входящий размер запроса/таймауты/соединения на proxy; не доверять клиентским IP-заголовкам без настройки доверенного proxy. Задать минимум два healthcheck: доступность приложения и БД. Не включать тела комментариев, вопросы ИИ, SQL-параметры, токены и cookie в логи.

Каждый час выполнять `npm run maintenance` для очистки истёкших счётчиков и сессий. Эта команда не удаляет документы и комментарии. Архивные материалы не помещать в `public`, иначе контроль доступа API можно обойти.

## Резервная копия и проверка восстановления (локальный PostgreSQL)

Копии БД содержат данные пользователей и хеши паролей; хранить приватно, вне Git. Не использовать `docker compose down -v` как способ перезапуска.

```sh
mkdir -p .local/backups
chmod 700 .local/backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > .local/backups/archive.dump
chmod 600 .local/backups/archive.dump
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" archive_restore_test'
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d archive_restore_test --exit-on-error' < .local/backups/archive.dump
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d archive_restore_test -c '\''SELECT count(*) FROM "Document";'\'''
```

Создание восстановительной БД выполняется один раз; для следующей проверки выбрать новое имя. Не восстанавливать поверх рабочей БД. Отдельно копировать FILE_STORAGE_ROOT и проверять доступность файлов по метаданным восстановленной БД; `pg_dump` не включает сами PDF. Перед реальным запуском настроить расписание копий, срок хранения, шифрование и практическую проверку восстановления у выбранного провайдера.

## Модули Артура и оставшиеся внешние требования

MODERATION_SERVICE_URL/TOKEN и ASSISTANT_SERVICE_URL/TOKEN нужны только для подключения его сервисов; без фильтра комментарии ждут ручной проверки, без ИИ endpoint возвращает 503. Форматы описаны в API.md. Секрет LLM хранит сервис Артура, браузер его не получает. При выборе провайдера проверить доступ и жёсткий бюджет расходов.

Публичный HTTPS-стенд ещё не создан: хостинг, домен и учётные данные провайдера не предоставлены. Текущие изменения не публикуют сайт и не меняют опубликованную облачную конфигурацию.
