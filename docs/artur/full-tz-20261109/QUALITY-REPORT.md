# A08 — отчёт по корпусу и разрешённым агрегатам

Отчёт не собирает посещения и не создаёт таблицы событий. Использует существующие публикации CMS/каталога и отдельный строгий адаптер будущих агрегатов B10. Пороги — технические предложения, не утверждённая политика архива.

## Текущий корпус

`GET /api/admin/assistant/quality[?branchId=ID&reviewAfterDays=180]` — авторизованный сотрудник с `analytics.read`. Пресет ANALYST уже содержит это право. Редактор/архивист без дополнительного права получает 403. Проверяются текущие права/активность/сессия и область филиала; передача чужого branchId не расширяет доступ. Ответ `Cache-Control: no-store`. Отчёт только читает публикации, не одобряет и не публикует их.

Источник — один RepeatableRead-снимок реальной БД. Учитываются публичные филиалы и общие материалы, если разрешена глобальная область. SETTING/внутренний ARCHIVE_DOCUMENT исключены из информационного корпуса; документы считаются отдельно. Черновики, снятые редакции и удалённые/непубличные карточки не увеличивают покрытие. Старый nullable revision допускается лишь для неуправляемой RU-проекции; новые переводы требуют связи с PUBLISHED-редакцией, её правильного языка/материала и независимого reviewer.

Возвращаются только количества: опубликованные материалы и демонстрационные материалы, языковое покрытие/пробелы RU/KK/EN, согласованные карточки с ограниченной копией, кандидаты на повторную проверку и ошибки целостности публикаций. Заголовки, тексты, адреса/телефоны/email, служебные причины, ID сотрудников, исходные запросы посетителей и байты файлов в отчёт не попадают. Для сравнения reviewer/author их ID читаются сервером и не выводятся. Лимит — 20 000 материалов суммарно; при превышении `503 QUALITY_SCAN_LIMIT`, а не тихо усечённые цифры. Для большого корпуса нужен отдельный пакетный/SQL-агрегированный процесс и измерение нагрузки.

`reviewAfterDays` — от 1 до 3650, по умолчанию 180. Возраст текущей публикации даёт рекомендацию **проверить** материал, не утверждение, что сведения неверны. Новый черновик не освежает дату действующей публикации. Это не срок хранения/удаления и не юридический регламент.

Каждая рекомендация содержит `action`, `corpus`, при необходимости `locale`, измеренный `count`, `owner`, `method=corpus-rule`, `requiresHumanReview=true`. Выбор и объяснение — правила; `modelContribution=none-in-corpus-report`. Обученная модель не приписывается арифметике. `traffic={status:not-connected, searches:null, emptyResults:null}` означает отсутствие подключения измерений, а не нулевую посещаемость.

Браузерный DTO: [assistant-quality.ts](../../../src/contracts/assistant-quality.ts). Интерфейс отчёта — R-F03 Алинура; endpoint уже позволяет подключить его без выдачи аналитику прав редактирования.

## Агрегаты поиска

`aggregate-quality-report.ts` принимает только version/sourceType/measuredAt/rows. Источник явно `synthetic` или `supplied-aggregate`; `policyApprovalVerified=false` не позволяет принять подпись входного файла за доказанное разрешение сбора. Каждая строка содержит только фиксированный topicId, полуоткрытый период `[start,end)` и неотрицательные целые searches/emptyResults/stalePages. Лишние поля, email/ID/сырой запрос, неизвестная тема, невозможные счётчики, незавершённые/пересекающиеся/дублированные окна отвергаются.

Группы с searches < 5 скрываются вместе с числами. Хеш считается **после подавления**, чтобы маленькие числа нельзя было перебрать по хешу исходного входа. Непереданная тема обозначена как неизмеренная, измеренный ноль не превращается в отсутствие измерения. Доля пустых поисков ≥ 30% предлагает проверить поиск/справку, stalePages > 0 — проверить переданный флаг страницы. Порог/флаг требуют согласования; реальная посещаемость из них не выдумывается.

`quality-topic.ts` может локально определить только ID известной темы собственной моделью, без сохранения вопроса. Это опциональный шаг до агрегации; сам отчёт использует статистические правила. Автоматическая отправка событий/обучение на них не добавлены. Сбор реальных событий и его основание остаются R-A05/B10 с архивом.

```sh
mkdir -p .local/assistant-quality
npm run report:quality -- --input data/artur/quality-aggregate-example.json --output .local/assistant-quality/example.json
```

Пример исключительно синтетический: 20 поисков/8 пустых/2 страницы к проверке. Файл результата должен быть новым; существующий не перезаписывается. Код 0 — отчёт записан, 2 — ошибка аргументов/входа/записи; значения ошибочного входа не печатаются. Максимум входа 2 MiB и 10 000 строк, формат строгий. Клиент не должен посылать частные события в этот CLI/модуль.

Проверки: `npm test` (чистая арифметика, подавление/хеш, периоды, приватные поля и CLI), `test:cms-assistant` (настоящие login/роль/филиал/отзыв/публикация/перевод), `test:semantic` (семь реально опубликованных демонстрационных карточек, переводы и ограниченная копия). Воспроизводятся на отдельной БД с суффиксом `_test`, не на данных пользователя. Фактические результаты сохраняются после завершения прогонов; наличие файла инструкции не объявляет тест успешным.
