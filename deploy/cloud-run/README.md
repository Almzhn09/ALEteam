# ALEteam: обновление сайта в Google Cloud Run

В авторизованном Cloud Shell, из корня существующей копии ALEteam, выполните одну команду:

```bash
git fetch origin && git switch main && git pull --ff-only origin main && bash deploy/cloud-run/update.sh
```

Финальный выпуск берётся из `main`. Ожидание времени отменено; `release-deadline.sh` для обновления не нужен. Требуются Git, gcloud и Python 3; Node/npm/NVM в Cloud Shell не нужны — приложение собирается внутри Docker.

`update.sh` собирает текущий checkout и обновляет образ **только** сервиса `ale-archive-preview` в проекте `saq-qurylys`, регионе `europe-west1`. Сервис `saq-qurylys-api` не изменяется. Если постоянная БД уже подключена, переменные, секреты, настройки входа и строка подключения сохраняются. Строки подключения не выводятся.

## Постоянный PostgreSQL (Neon)

Если у существующего сервиса ещё нет `DATABASE_URL`, `update.sh` сам запускает `connect-database.sh` и запрашивает прямую строку Neon скрытым вводом. В Neon Connect отключите Connection pooling, используйте прямой URL с `sslmode=require`. Не отправляйте его в чат или GitHub.

Скрипт сохраняет URL отдельной версией Google Secret Manager и даёт сервисному аккаунту сайта доступ к этому секрету. Новая ревизия использует внешний PostgreSQL; остальные настройки сервиса, пароль администратора и секрет сессий сохраняются. Cloud SQL и Firebase не создаются.

Исходный снимок восстанавливается **только в пустую** базу, одной транзакцией, под блокировкой. В существующей базе архива применяются отслеживаемые миграции, файлы восстанавливаются по SHA, прикрепляется отсутствующий R01. Чужая непустая база отклоняется. Повтор не сбрасывает аккаунты и сессии, не создаёт дубли и не возвращает отозванные/отклонённые вложения.

При переходе со старого временного контейнера на новый пустой проект Neon аккаунты и пользовательские изменения из временного контейнера автоматически не переносятся: постоянный проект начинается с исходных материалов и штатного администратора. Текущие обновления уже подключённой постоянной БД сохраняют её данные.

## Проверка обновления

После update/connect-database автоматически выполняется `check-public.py`: публичные страницы, все оригиналы/превью опубликованных RU/KK/EN-редакций по точному SHA-256, обязательный полный R01 на странице платных услуг и равнозначность четырёх названий города. Отсутствие файла или неравнозначный поиск завершает команду ошибкой. Это проверка только чтения, без регистраций в рабочей БД. `ALE_SKIP_PUBLIC_CHECK=1` применяется только в тестах с подставным gcloud.

R01 — 15-страничный официальный PDF прейскуранта, 1 636 084 байта, SHA-256 `6480e6fd39bbf0f48c7c8396028da57d29cbec405c44a83a3ede7d575fad3b8f`. Он включён в исходный снимок и публикуется штатным CLI при обновлении постоянной БД, если ещё отсутствует. Runtime копируется одним подготовленным каталогом с теми же путями и bundled CLI, чтобы сборка не исчерпывала диск на Docker с драйвером vfs.

Локальная приёмка собранного образа `aleteam-cloud-preview:local` в собственных одноразовых контейнерах:

```bash
ALE_CLOUD_TEST_PORT=3134 node tests/cloud-run-preview.mjs
ALE_CLOUD_TEST_PORT=3134 ALE_CLOUD_BROWSER_CHECKS=1 node tests/cloud-run-persistent.mjs
```

Вторая команда дополнительно проверяет публичные оригиналы, фотографии, вопросы и ссылки ИИ, страницы 2 и 15 PDF, дочитывание DOCX, ошибки файлов, индикатор перехода, регистрацию и RU/KK/EN в Chromium через Playwright. Нужны Docker, зависимости проекта и Chromium (`/usr/bin/chromium`). Учётные записи создаются только в собственной базе `archive_release_test`; контейнеры и тестовые секреты удаляются после прогона. Рабочая Neon не используется.

`node --test tests/cloud-run-update.test.mjs tests/cloud-run-source-files.test.mjs` проверяет сохранение секретов и восстановление файлов с подставным gcloud, без изменений облачных ресурсов. Полные результаты финальной интеграции: [docs/final-integration-20261112](../../docs/final-integration-20261112/README.md).

## Ограничения

Оригиналы из репозитория восстанавливаются в файловое хранилище при запуске. **Новые пользовательские загрузки требуют отдельного постоянного файлового хранилища**: подключение PostgreSQL само по себе этого не решает. Почтовая доставка и сброс пароля через почту не подключены. Публичная автоматическая проверка не проверяет почту и авторизованного ИИ.

Cloud Build, Artifact Registry, Cloud Run и Secret Manager имеют собственные квоты и тарифы; нулевая стоимость не гарантируется. Исторический профиль `deploy.sh` использует временный PostgreSQL внутри контейнера и предназначен для отдельного показа. Для обновления опубликованного сайта применяется команда из `main` в начале этой инструкции.
