# Docker-стенд ALEteam

Подготовлен по выбранному варианту «хостинга пока нет». Запускает реальное приложение, PostgreSQL и постоянное хранилище документов. Не создаёт публичный адрес, аккаунт хостинга и официальный сайт архива. Проверки пакета: [DEPLOYMENT-VALIDATION.md](../docs/DEPLOYMENT-VALIDATION.md).

## Запуск на своём компьютере

Нужны Git, Node.js 24 и работающий Docker с Compose v2. Из корня репозитория:

```sh
npm run deploy:setup
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build --wait app
```

После запуска открыть `localhost:3100` **на том компьютере, где запущен Docker**. Это не ссылка на облачную машину чата. Сайт использует настоящие API, БД, встроенный фильтр и поиск по источникам; моки выключены. `npm ci` на компьютере не нужен — зависимости устанавливаются внутри образов.

`deploy:setup` создаёт игнорируемый Git файл `deploy/.env` со случайными паролями/ключом сессий и правами 0600. Уже существующий файл сохраняется. Демоавтор — author@example.test, модератор — moderator@example.test; их пароли находятся в этом приватном файле, в DEMO_AUTHOR_PASSWORD и DEMO_MODERATOR_PASSWORD. Не добавлять файл в Git и не передавать значения в чат.

Вход/регистрация: доступны подготовленные демоучётные записи; публичной регистрации пока нет. `ALLOW_DEMO_SEED=1` разрешает только оригинальный вымышленный корпус: 20 документов, 5 PDF и 5 PNG. Для собственной БД отключить seed после подготовки данных. Ключ LLM не требуется для локального retrieval; платный провайдер по умолчанию не вызывается.

Приложение и инструменты работают как node (UID 1000). Для app создана роль PostgreSQL archive_app без SUPERUSER/CREATEDB/CREATEROLE; административный пароль приложению не передаётся. Роль владеет схемой, поскольку ею выполняются миграции этого прототипа. БД не имеет опубликованного порта. Только app доступен на loopback; HTTPS — отдельный профиль.

## Сборка в управляемой облачной среде с прокси

В текущей облачной машине необходим публичный CA сеанса. Он монтируется только на сетевой шаг сборки, не входит в образ; TLS и integrity пакетов не отключаются:

```sh
docker build --secret id=proxy_ca,src="$CODEX_PROXY_CERT" --target runtime -t aleteam:local .
docker build --secret id=proxy_ca,src="$CODEX_PROXY_CERT" --target tools -t aleteam-tools:local .
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --wait --no-build app
```

На обычном компьютере с публичными сертификатами дополнительные CA/флаги не нужны. Если корпоративная сеть использует свой доверенный CA, передать его через такой же BuildKit secret. Не использовать strict-ssl=false или отключение контрольных сумм.

## Остановка и обновление

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml stop
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --wait --no-build app
```

База и файлы остаются в named volumes. Для обновления сначала сделать backup, затем собрать новые образы и выполнить up с --build. Миграции завершатся до запуска приложения. Не выполнять down -v на рабочем стенде: эта команда удаляет постоянные данные. Не менять пароли БД в .env как способ ротации существующей базы — init выполняется только для нового тома; ротация требует отдельного изменения роли.

## Резервная копия и восстановление

```sh
npm run deploy:backup -- --directory .local/stand-backup-01
```

Путь должен быть новым: предыдущая копия не перезаписывается. Создаются database.dump, files.tar и manifest.json с размером, SHA-256 и ID образа. Каталог 0700, файлы 0600, Git их игнорирует. Копия содержит обсуждения, учётные записи и хеши паролей; хранить её приватно на отдельном носителе. Секреты окружения в копию не входят — их хранить отдельно в защищённом менеджере. Не запускать импорт/seed одновременно с копированием файлов: pg_dump согласован для БД, а архив файлов снимается следом.

Восстановление выполняется **только в новый проект** с новыми томами; текущий стенд не очищается. Подготовить приватный `deploy/.env.restore` на основе своего .env: другой DEPLOY_HTTP_PORT (например 3101), BETTER_AUTH_URL=http://localhost:3101, ALLOW_DEMO_SEED=0. Сохранить необходимые секреты и параметры базы; не публиковать файл. Требуются ранее собранные локальные образы.

```sh
npm run deploy:restore -- --project ale-restore-01 --env deploy/.env.restore --directory .local/stand-backup-01
```

Сначала проверяются SHA-256 и отсутствие контейнеров/томов целевого проекта. Затем восстанавливаются база и файлы, проверяются миграции, запускается app. При ошибке частичный новый проект сохраняется для диагностики, исходный не изменяется. Использовать только собственную доверенную копию: checksum проверяет целостность, не авторство SQL/tar. Проверить health, вход, существующий комментарий и PNG перед переключением реального трафика.

Автотест: `node tests/deploy.mjs`. Он создаёт собственные уникальные проекты и случайные локальные порты, проверяет запись/перезапуск/копию/восстановление и удаляет только свои контейнеры/тома. Приватные копии остаются в .local; в отчёт .local/deploy-validation.json секреты не входят.

## Позже: общий HTTPS-адрес

Когда появятся сервер и домен: направить DNS на сервер, разрешить входящие 80/443, создать .env через `npm run deploy:setup -- --domain archive.example.kz` с **вашим** доменом. Если .env уже существует, изменить только DEPLOY_DOMAIN и BETTER_AUTH_URL=https://ваш-домен, сохранив пароли. Затем:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml --profile public up -d --build --wait
```

Caddy хранит сертификаты в отдельном томе и автоматически обслуживает HTTPS. Конфигурация Caddy проверена, но выпуск реального сертификата и публичный сайт ещё не проверены: сервера и домена нет. Для LLM отдельно настроить серверные ARCHIVE_LLM_API_KEY/MODEL, бюджет провайдера и ASSISTANT_MODE=llm. Внешние вызовы из контейнера в управляемой прокси-среде также требуют разрешённого домена и смонтированного доверенного CA; обычный Docker-стенд вне этой среды использует публичные CA.

## Если запуск не прошёл

Проверить Docker/Compose, свободен ли 3100, наличие env-файла, `docker compose ... ps` и логи app/setup/db. Не публиковать env/config dumps и приватные логи с данными. Для Linux init-файл deploy/db-init.sh должен быть читаем пользователем postgres внутри контейнера (обычно 0644); LF фиксируется в .gitattributes. Новые файлы БД/документов не должны зависеть от временного контейнерного слоя. Прототип использует Prisma JS/WASM, поэтому предупреждение генератора о версии native OpenSSL не заменяет функциональную проверку: поиск/запись/восстановление реально проверены с JS-драйвером.
